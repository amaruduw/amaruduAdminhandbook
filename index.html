Welcome to the Salesforce Platform. This section covers the foundational concepts every Salesforce Administrator must master. Understanding these basics is essential before diving into more complex configurations.

1.1 Developer Edition Setup

Concept Explanation

The Salesforce Developer Edition (DE) is a free, full-featured copy of the Salesforce platform designed for development and testing. It provides access to nearly all Salesforce features, making it the perfect environment for learning and experimentation.

Why It Matters

  • Risk-free learning environment - mistakes don't affect production data
  • Access to enterprise features without licensing costs
  • Ideal for certification exam preparation
  • Safe place to test configurations before deploying to production

Step-by-Step Implementation

  1. Navigate to developer.salesforce.com/signup
  2. Fill in the registration form with accurate information
  3. Choose a unique username (email format)
  4. Select your preferred language and locale
  5. Verify your email address
  6. Set up security questions for account recovery
  7. Log in to your new Developer Edition org

Real-World Example

Sarah, an aspiring Salesforce Admin, signs up for a Developer Edition to practice for her certification exam. She uses this org to build a complete sales process from scratch, including custom objects, automation rules, and dashboards. When she interviews for a Salesforce Admin position, she demonstrates her hands-on experience by showing the hiring manager her fully configured DE org, giving her a significant advantage over other candidates.

Common Pitfalls

  • Using production data in DE - always use sample/test data
  • Not documenting changes made for experimentation
  • Letting the org become cluttered with unused configurations
  • Forgetting that DE orgs can be deactivated after periods of inactivity

Certification Tips

For the Salesforce Administrator Certification exam, understand that Developer Edition provides the same functionality as Enterprise Edition for learning purposes. Know the signup process and the types of orgs available (Developer, Sandbox, Production, Scratch Orgs).

1.3 Core Platform Concepts

Tabs, Objects, Records, and Fields

Understanding the fundamental building blocks of Salesforce is crucial. These four elements form the foundation of all data storage and user interaction on the platform.

Tabs

Navigation elements that provide access to objects and web content. Think of tabs as the doors to different rooms in your Salesforce house.

Objects

Database tables that store specific types of information. Standard objects (Account, Contact, Opportunity) come with the platform; Custom objects are created by administrators.

Records

Individual rows in an object table. Each record represents one instance of that object type (e.g., one Account record = one company).

Fields

Columns in an object table that store specific data points. Fields define what information can be stored about each record.

Object Manager

The Object Manager is the central administration interface for managing all objects in your org. Access it via Setup > Object Manager. From here, administrators can:

  • Create and modify custom objects
  • Add, edit, and delete fields
  • Configure page layouts and compact layouts
  • Set up validation rules and record types
  • Manage relationships between objects
  • Configure buttons, links, and actions

Company Information

Company Information in Salesforce stores critical organizational details. Access via Setup > Company Settings > Company Information. Key settings include:

  • Organization Name and Address
  • Default Locale, Language, and Time Zone
  • Default Currency (for single-currency orgs)
  • Fiscal Year Settings
  • Organization Edition and Limits

Users & Login History

User management is a core administrative function. Navigate to Setup > Users > Users to manage user accounts. Key capabilities include:

  • Create, edit, and deactivate user accounts
  • Reset passwords and unlock accounts
  • Assign profiles, permission sets, and roles
  • View and export login history
  • Monitor user activity and license usage

Login History

Login History tracks all login attempts to your org. Access via Setup > Users > Login History. This report shows:

  • User who attempted to log in
  • Login timestamp
  • Source IP address
  • Login status (success/failure)
  • Browser and application used

Audit Trails

Salesforce provides multiple audit trail capabilities:

Setup Audit Trail

Tracks changes made to your org's configuration. Shows who made what changes and when. Retains 20 most recent changes per user, up to 6 months.

Field History Tracking

Tracks changes to field values on records. Must be enabled per object and per field. Retains data for up to 18 months (standard) or 10 years (with add-on).

Record Modification Audit

Standard fields (Created By, Created Date, Last Modified By, Last Modified Date) automatically track record changes.

2.1 Custom Objects

Concept Explanation

Custom objects are database tables that you create to store information specific to your organization. While Salesforce provides standard objects like Accounts and Contacts, custom objects allow you to extend the platform to meet unique business requirements.

Why It Matters

  • Extends Salesforce to match your business processes
  • Creates structured storage for unique data types
  • Enables custom automation and validation
  • Supports reporting and analytics on custom data

Step-by-Step Implementation

  1. Navigate to Setup > Object Manager
  2. Click 'Create' and select 'Custom Object'
  3. Enter Label (plural and singular)
  4. Enter Object Name (API name, ends with __c)
  5. Enter Description (optional but recommended)
  6. Select Record Name type (Text or Auto Number)
  7. Configure optional features (Reports, Activities, etc.)
  8. Set Deployment Status (In Development or Deployed)
  9. Save the object

Real-World Example

A property management company needs to track rental units. The admin creates a custom object 'Rental Unit' with fields for Address, Monthly Rent, Number of Bedrooms, and Occupancy Status. They enable Reports to create occupancy dashboards, enable Activities to track maintenance requests, and enable Field History to monitor rent changes over time. This custom object becomes the foundation of their property management system.

2.5 Object Relationships

Concept Explanation

Relationships define how objects connect to each other. They enable you to link records across objects, creating a cohesive data model that reflects real-world business connections.

Lookup Relationship

A Lookup relationship creates a loose association between two objects. The child record references a parent record, but the relationship is optional and doesn't enforce data integrity.

  • Child can exist without parent
  • Parent deletion doesn't affect child records
  • Up to 40 lookups per object
  • Can be multiple levels deep
  • Supports cross-object formulas

Master-Detail Relationship

A Master-Detail relationship creates a tight parent-child bond where the child (detail) is dependent on the parent (master). This relationship enforces data integrity and enables roll-up summary fields.

  • Child cannot exist without parent (required field)
  • Parent deletion cascades to all child records
  • Up to 2 master-detail relationships per object
  • Enables roll-up summary fields
  • Child inherits parent's sharing settings
  • Child's owner is always the master record's owner

Many-to-Many Relationships

Salesforce doesn't support direct many-to-many relationships. Instead, use a Junction Object - a custom object with two master-detail relationships that links two objects together.

Example: Students and Courses

Students can enroll in multiple Courses, and Courses can have multiple Students. Solution: Junction Object 'Enrollment' with Master-Detail to both Student and Course.

Self-Relationship

A self-relationship is a lookup from an object to itself. Useful for hierarchical data like employee-manager relationships or parent-child accounts.

Hierarchical Relationship

A special lookup relationship available only on the User object. Creates a hierarchy for approval processes and delegation.

Real-World Example

An e-commerce company needs to model their order system. They create:

  • Order (Master) with Order Line Items (Detail) - Master-Detail
  • Order Line Item looks up to Product - Lookup
  • Customer Account has self-relationship for parent company - Self Lookup
  • Products and Categories use Junction Object for many-to-many

This model allows them to track orders with line items, associate products flexibly, and manage corporate hierarchies.

2.6 Roll-Up Summary Fields

Concept Explanation

Roll-Up Summary fields calculate values from a set of related detail records and display the result on the master record. They are only available on the master side of a Master-Detail relationship.

Available Operations

  • COUNT: Total number of related records
  • SUM: Total of a numeric field across related records
  • MIN: Lowest value of a field across related records
  • MAX: Highest value of a field across related records

Step-by-Step Implementation

  1. Navigate to the master object's fields
  2. Create new field with type 'Roll-Up Summary'
  3. Select the Master-Detail relationship
  4. Choose the aggregation type (COUNT, SUM, MIN, MAX)
  5. For SUM/MIN/MAX, select the field to aggregate
  6. Optionally add filter criteria
  7. Save the field

Real-World Example

A project management company tracks tasks within projects. The Project object (master) has a Roll-Up Summary field 'Total Estimated Hours' that sums the Estimated Hours field from all related Task records (detail). They also have 'Open Task Count' using COUNT with a filter for Status != Completed. Project managers can see project scope at a glance without running reports.

Limitations

  • Maximum 25 roll-up summary fields per object
  • Only works with Master-Detail relationships
  • Cannot reference formula fields that use cross-object references
  • May impact performance with large data volumes

  • Number: Returns numeric value
  • Percent: Returns percentage

User Management

User management is at the heart of Salesforce administration. Understanding how to create users, assign permissions, and control access is essential for maintaining a secure and efficient organization.

3.1 User Creation

Concept Explanation

Users are individuals who can log in to Salesforce. Each user has a unique username (in email format), a profile that determines their base permissions, and optionally roles and permission sets for additional access.

Step-by-Step Implementation

  1. Navigate to Setup > Users > Users
  2. Click 'New User'
  3. Enter user's name and email
  4. Enter unique username (email format)
  5. Select User License type
  6. Assign a Profile
  7. Select a Role (optional but recommended)
  8. Set Locale, Language, and Time Zone
  9. Configure email options
  10. Save the user record

User Licenses

User licenses determine the baseline features available to a user. Common license types include:

Salesforce License Full platform access
Salesforce Platform Custom app access only
Chatter Free/Chatter External Limited Chatter access
Community/Partner/Customer External user access
Service Cloud/Field Service Specific cloud features

Real-World Example

A company hires a new sales representative. The admin creates a user with a Salesforce license, assigns the 'Standard Sales User' profile, and places them in the 'Sales Rep' role within the role hierarchy. They also assign the 'Advanced Reporting' permission set to give access to additional report types. The new user receives an email with login instructions and can immediately start working with the appropriate level of access.

Common Pitfalls

  • Using generic/shared user accounts (violates security best practices)
  • Not deactivating users who leave the company
  • Assigning overly permissive profiles to new users

3.3 Permission Sets

Concept Explanation

Permission sets are collections of permissions that grant additional access to users without changing their profile. A user can have multiple permission sets, making them ideal for temporary or specialized access needs.

Why Use Permission Sets

  • Avoid profile proliferation (too many similar profiles)
  • Grant temporary elevated access
  • Handle exceptions without creating new profiles
  • Easily assign/remove access as needed
  • More granular than profiles for specific needs

Permission Set Types

  • Standard Permission Sets: Created by administrators for custom permission combinations
  • Session-Based Permission Sets: Activated during specific sessions (e.g., elevated access for maintenance)
  • Permission Set Groups: Collections of permission sets assigned together

Creating a Permission Set

  1. Navigate to Setup > Users > Permission Sets
  2. Click 'New'
  3. Enter Label and API Name
  4. Select User License (or None for all licenses)
  5. Save and configure permissions
  6. Assign to users as needed

Real-World Example

A manufacturing company has sales reps who occasionally need to approve discounts over 20%. Instead of creating separate profiles, the admin creates a 'Discount Approver' permission set that grants edit access to the Discount field and access to an approval process. When a rep needs this capability, the permission set is assigned. When they no longer need it, it's removed. This keeps the profile structure clean and manageable.

5.1 Validation Rules

Concept Explanation

Validation rules enforce data quality by preventing users from saving records that don't meet specified criteria. When a validation rule fails, an error message displays and the record is not saved.

Step-by-Step Implementation

  1. Navigate to Object Manager > [Object] > Validation Rules
  2. Click 'New'
  3. Enter Rule Name
  4. Create the Error Condition Formula
  5. Enter Error Message
  6. Select Error Location
  7. Save and activate

Common Validation Rule Patterns

Require Close Date for Closed Opportunities AND(ISPICKVAL(StageName, "Closed Won"), ISBLANK(CloseDate)) Error: Close Date is required for closed opportunities.
Discount Cannot Exceed 30% Discount_Percent__c > 0.30 Error: Discount cannot exceed 30%.
End Date Must Be After Start Date End_Date__c < Start_Date__c Error: End Date must be after Start Date.
High Value Deals Require Approval AND(Amount > 100000, ISPICKVAL(Approval_Status__c, "Not Submitted")) Error: Deals over $100,000 require manager approval.

Order of Execution

Validation rules fire at specific points in the save process:

  4. After triggers execute
  5. Assignment rules execute
  6. Auto-response rules execute
  7. Workflow rules execute
  8. Escalation rules execute

Workflow Components

  • Rule Criteria: Conditions that must be met
  • Immediate Actions: Execute immediately when criteria met

Workflow Actions

  • Email Alert: Send email to designated recipients
  • Task: Create task for specified user
  • Outbound Message: Send data to external system

Evaluation Criteria

  • created: Rule evaluates only when record is created
  • created, and every time it's edited: Evaluates on create and every edit
  • created, and any time it's edited to subsequently meet criteria: Evaluates when record changes from not meeting to meeting criteria

7.2 Time-Dependent Workflow Actions

13.2 Salesforce Admin Interview Q&A

What is the difference between a Role and a Profile?
A Profile controls what a user can do (object permissions, field access, app visibility). A Role controls what a user can see (record visibility through role hierarchy). Every user must have one profile and can optionally have one role.
When would you use a Permission Set instead of creating a new Profile?
Use Permission Sets for exceptions to the standard profile permissions. They're ideal for granting temporary or specialized access without creating profile proliferation. A user can have multiple permission sets but only one profile.
Explain the Salesforce security model in order.
Security is applied in layers: 1) Org-level (login restrictions), 2) Object-level (CRUD permissions), 3) Field-level (visibility), 4) Record-level (OWD, role hierarchy, sharing rules, manual sharing).
What is the difference between Lookup and Master-Detail relationships?
Lookup is a loose relationship - child can exist without parent, deleting parent doesn't affect child. Master-Detail is tight - child requires parent, deleting parent deletes all children, enables roll-up summaries, and child inherits parent's sharing.
When should you use Flow Builder instead of Workflow or Process Builder?
Salesforce is retiring Workflow and Process Builder. Flow Builder should be used for all new automation. It handles simple updates, complex logic, user interactions, and scheduled processes all in one tool.
How would you handle a requirement to share records with users outside the role hierarchy?
Use Sharing Rules for systematic sharing based on criteria or ownership. For one-off needs, use Manual Sharing. For complex scenarios, consider Apex Managed Sharing.
What are Governor Limits and why do they exist?
Governor Limits enforce the multi-tenant architecture by preventing any single org from consuming excessive resources. Common limits include 100 SOQL queries and 150 DML statements per transaction.
How do you troubleshoot a flow that isn't working as expected?
Use the Debug tool to step through execution, check variable values at each step, verify element connections, and review debug logs. Add temporary Screen elements to display intermediate values.
What is the difference between a Summary and Matrix report?
Summary reports group data by up to three fields in a vertical list with subtotals. Matrix reports group by both rows and columns, creating a grid view similar to a pivot table.
How would you design a data model for tracking student course enrollments?
Create Student and Course objects, then a Junction Object 'Enrollment' with Master-Detail relationships to both. The Enrollment object stores enrollment date, grade, and status. This enables many-to-many relationships with reporting on both sides.
